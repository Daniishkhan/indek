# Indek — UX & Feature Document

## 1. Purpose

This document is the bridge between the PRD and the code. It enumerates the features the product needs at v1, the surfaces those features live on, and the user journeys that thread them together. It is deliberately lean: nothing in here is a "nice to have." If a feature is described in this document, it ships in v1; if it isn't, it doesn't.

What this document does _not_ do: specify pixel layouts, color systems, component libraries, or interaction micro-detail. Those decisions belong to the implementation phase. This document specifies _what_ must be possible and _in what order the user does it_, not _what it looks like_.

## 2. Design principles

1. **One screen per decision.** The operator's day and the rider's day are made up of small decisions made under time pressure. Each screen should be built around one decision the user is making at that moment.
2. **No empty states without an action.** Every list, board, and queue surfaces the next thing to do.
3. **Tap counts matter on the rider side.** The rider is standing at a customer's door, sometimes in the heat, sometimes with the customer watching. The happy-path delivery should be completable in five taps or fewer.
4. **Reconciliation closes loops, not opens them.** End-of-shift screens don't ask the operator open-ended questions. They surface what doesn't match and force a decision (accept variance with reason, or fix the data).
5. **The merchant surface stays lightweight.** In the MVP it supports approval-gated signed-in access, delivery request entry, status visibility, and finance document visibility without turning into a full merchant admin system.

## 3. The three surfaces

Indek has three distinct user surfaces, each with its own access pattern, device assumption, and information density.

- **Operator console.** A desktop-first web app. The operator sits at a laptop or tablet and runs the day. Information-dense; built for seeing the whole operation at once. Authenticated. It now includes a dedicated finance module inside the admin surface.
- **Rider PWA.** A mobile-first progressive web app installed on the rider's Android phone. Built for one-handed use, sunlight readability, and tolerating spotty connectivity. Authenticated via a simple sign-in tied to the rider's profile.
- **Merchant surface.** A lightweight merchant experience with two entry paths: an approved signed-in workspace for request entry and finance visibility, and tokenized link views for low-friction status/remittance access. The signed-in workspace is blocked until admin approval. Token links remain unguessable and scoped to one merchant.

### Operator information architecture

The operator console should be understood as five modules:

- **Overview**
- **Intake**
- **Dispatch**
- **Live ops**
- **Finance**

The finance module is an admin-only money hub with sections for:

- **Reconciliation**
- **COD drop**
- **Remittances**
- **Billing invoices**
- **Tax review**
- **CSV exports**
- **Email outbox/history**

Implementation should treat this as the `/operator/finance/*` route family inside the operator console.

## 4. Core user journeys

The product's whole reason to exist is to make the courier's core journeys faster, safer, and more reconcilable than they are in a manual, phone-and-spreadsheet workflow. Everything else is supporting infrastructure for these.

### Journey 0 — Merchant: register and wait for approval

A merchant opens the registration route and submits their basic identity details. Indek creates the merchant account in `pending_approval`. The merchant then sees a clear pending screen explaining that the admin must approve access before the signed-in merchant workspace becomes available.

The merchant can be shown lightweight status text and next-step guidance, but they cannot enter the full signed-in merchant workspace until an operator approves them.

### Journey 0b — Operator: review and approve a merchant

The operator opens the merchant approval queue from the admin console. Each pending merchant record shows the applicant details, the target merchant business record or matching merchant profile if one exists, and the actions to approve, reject, or suspend. Approving the merchant unlocks the signed-in merchant workspace. Rejecting or suspending keeps the account blocked.

This journey is deliberately admin-controlled. Merchant approval is not automatic.

### Journey 0c — Operator: manage rider access

The operator creates rider access from the admin console, ties it to the rider record, and decides whether the rider is active. The same screen lets the operator deactivate or remove rider access later. Riders never self-register.

This is not the shift-status workflow. It is the access-control workflow for who is allowed into the rider PWA at all.

### Journey 1 — Merchant: create a delivery request (daily)

A merchant opens the signed-in merchant workspace or their tokenized merchant page and creates a delivery request. The form captures customer name, phone, pickup address, delivery area, delivery address, COD amount, item description, and notes. As the merchant fills in the addresses, Indek shows an average shipping charge based on the configured route or zone rules. When the merchant submits, the request lands in Indek in a review queue, not directly on a rider manifest.

This is the default intake path in v1. It should be lightweight enough that the merchant can submit a request in under a minute without needing the operator to re-enter the same data.

### Journey 2 — Operator: review the request and decide what happens next

The operator opens the review queue and sees every newly submitted merchant request. Each request card shows merchant, customer, pickup and delivery addresses, COD amount, item summary, and the average shipping estimate. The operator does basic due diligence: is the address serviceable, is the request complete enough to dispatch, does anything look risky or inconsistent, and does the merchant need to clarify something before ops sends a rider.

The operator has two primary actions:

- **Approve for dispatch:** the request moves into the dispatch-ready queue and can be assigned to a rider.
- **Send follow-up message:** the operator writes a short merchant-facing message tied to that request, asking for clarification or correction. The request stays blocked until the merchant updates it or ops resolves it manually.

This is not a chat product. It is a narrow request-review workflow that keeps the courier from dispatching bad requests.

### Journey 3 — Operator: build and assign a shift manifest (daily)

With unassigned parcels in the system, the operator opens the dispatch board. The left side shows unassigned parcels grouped by merchant pickup location. The right side shows the rider roster with status (available, on shift, off duty). The operator picks a rider, then taps parcels (or drags them) into that rider's pending manifest. As parcels are added, the manifest preview shows total parcel count, total expected COD, the pickup locations the rider will need to visit, and a rough zone summary based on the delivery addresses. When the operator is satisfied, they hit "Assign" — the manifest moves to the rider's queue, and the rider gets a notification on their PWA.

The operator can build multiple manifests in parallel and assign them in any order. There is no automatic balancing in v1 — the operator's judgment is the routing engine.

### Journey 4 — Rider: start shift and pick up parcels

The rider opens the PWA and sees their assigned manifest waiting. They tap "Accept" and the shift starts — a timestamped event. The manifest screen shows the pickup locations they need to visit (one per merchant), each with the count of parcels to collect. The rider goes to the first pickup, taps the location, and arrives at a scanning screen. They scan each parcel's QR label one by one; the screen shows a running count of "scanned vs. expected." When all parcels at this pickup are scanned, the rider hits "Confirm pickup" and the parcels move into the rider's custody. The rider repeats for each pickup location on the manifest.

If a parcel is missing at pickup or the merchant has an extra one not in the manifest, the rider taps "Report mismatch" and notes it; ops resolves it asynchronously. The shift continues.

### Journey 5 — Rider: deliver a parcel (the workhorse)

This is the journey the rider runs 15–25 times a day. It must be tight.

The rider opens the manifest, sees the list of parcels in custody, and taps the next one to deliver. The parcel screen shows: customer name, customer phone (tappable to call), address (with a tap-to-open-in-Maps link if a pin is attached), COD amount, item summary, and any notes from the merchant. The rider hits "Arrived" when they reach the location. The arrival screen presents three primary actions: **Delivered**, **Failed**, **Partial**.

- **Delivered (happy path):** The rider taps Delivered, takes a photo (camera opens directly), enters the customer OTP if the merchant requires one, confirms the cash amount collected matches the expected COD, and hits Done. The parcel state moves to delivered, the cash ledger updates, and the rider returns to the manifest list.
- **Failed:** The rider taps Failed, picks a reason from a short list (customer not home, customer refused, wrong address, customer asked for reschedule, other), optionally takes a photo, and hits Done. The parcel enters the reattempt queue and the rider returns to the manifest list.
- **Partial:** The rider taps Partial, enters the actual cash collected, picks a variance reason (customer kept some items, exact-change shortfall, customer renegotiated, other), takes a photo, marks which items the customer kept versus returned, and hits Done. Indek splits the parcel into a delivered portion (with the adjusted COD) and a returned portion (which enters the RTO flow). The rider returns to the manifest list.

The happy-path delivery is five taps: tap parcel → tap Arrived → tap Delivered → take photo → confirm. Variance flows are longer because they have to be — but they're never the default and never block the happy path.

### Journey 6 — Operator: monitor the day in progress (passive)

The operator's main screen during the day is the live operations view. It shows each rider on a card with: their current shift status, parcels in custody, parcels delivered today, cash held (with per-merchant breakdown on tap), and the time since their last logged event. Cards highlight when something is off — a rider with no logged event for over 30 minutes, a manifest with more failed attempts than expected, a cash variance brewing.

The operator does not actively manage the day from this screen. They watch it, and they intervene only when something looks wrong. Intervention means: tapping a rider card to see detail, fixing a data issue from the parcel detail view, or sending a follow-up back to the merchant if the original request needs correction.

### Journey 7 — Rider and operator: end-of-shift drop and reconciliation

When the rider has delivered or attempted everything on their manifest, they tap "End shift" in the PWA. The end-of-shift screen shows them their own summary: parcels delivered, parcels failed, parcels still in custody (which need to be returned), total cash collected per merchant. They hit "Ready to drop" — this notifies the operator that the rider is on the way back.

The rider arrives at the operator's location. The operator opens the rider's reconciliation screen on the desktop console. It shows two columns: **Expected** (what the system believes) and **Actual** (what the operator confirms in person).

- **Parcel reconciliation:** A list of parcels still in custody. The operator confirms each one is physically present (a tap per parcel, or a single bulk confirm if the count matches). Any parcel the system thinks is in custody but isn't physically there is flagged.
- **Cash reconciliation:** Total expected cash, broken down per merchant. The operator counts the cash the rider hands over and enters the actual total. If it matches, the shift can close. If it doesn't, the variance is highlighted in red and the operator must enter a reason code (rider float adjustment, cash short, cash over, counterfeit note, other) before the shift can close.

The operator hits "Close shift." The rider's shift ends, parcels still in custody are transferred to ops or back into the reattempt queue, and the cash ledger for that shift is locked.

This is the daily finance control point. The rider cash handover is not a background detail; it is the moment where COD truth, rider custody, and the admin’s reconciliation math all meet.

### Journey 8 — Operator: generate and send merchant remittance (per cycle)

On the agreed cycle (typically weekly), the operator opens the finance module, moves to the remittance section, picks a merchant, and sees a draft statement: every delivered parcel for the merchant in the period, the COD collected per parcel, the route-aware delivery fee and COD handling fee per parcel, the VAT or tax breakdown, and the net amount payable to the merchant. The operator reviews, hits "Finalize," and the system marks the statement as ready. The operator can then send the statement by email from the finance module, download the statement as a PDF or CSV export, and record the actual payment (bank transfer, cheque, cash) outside the system before marking the statement as settled.

If there are disputed parcels in the period, the operator sees them flagged at the top of the draft. They can put a hold on disputed amounts, which removes them from the current statement; the held amount carries forward to the next cycle once the dispute resolves.

### Journey 8b — Operator: issue and send a merchant billing invoice

The operator opens the finance module, moves to the billing section, picks a merchant, and prepares a billing invoice for courier service charges. The invoice is a separate document from remittance. It contains route-aware billable line items, totals, taxes, and its own document status. The operator can save it as draft, issue it, send it by email, export it as CSV, and later record it as paid or void.

This journey exists because the merchant needs both sides of the money picture: what the operator owes them, and what they owe the operator.

### Journey 8c — Operator: track finance email delivery

The operator opens the finance module's email outbox/history section and sees finance emails grouped by document type and send state. From here they can confirm whether a remittance statement or billing invoice was queued, sent, or failed, and they can retry a failed send without leaving the finance module.

This is a finance operational workflow, not a marketing email workflow. The same finance area should also expose CSV exports for reconciliation, COD handover, remittance, billing, and tax review.

### Journey 9 — Operator: look up a parcel for a dispute (as needed)

A merchant or customer asks "what happened with parcel X?" The operator goes to the parcel search, finds the parcel, and sees the full event log: every state transition with timestamp, rider, geolocation, photo, and OTP. The log answers the question without further investigation. If the dispute is valid, the operator can flag the parcel and put a hold on the related remittance amount.

### Journey 10 — Merchant: place a delivery request and check status (lightweight)

An approved merchant opens either the signed-in merchant workspace or the tokenized merchant link. A page opens with a compact order-request form at the top and the merchant's active and recently completed parcels underneath. The merchant enters customer name, phone, pickup address, delivery area, delivery address, COD amount, item summary, and notes. As soon as the pickup and delivery details are present, Indek shows an average shipping charge based on the merchant's configured route or zone pricing rules. The merchant sees the estimate before they submit, but ops still owns final assignment.

When the merchant submits the request, it enters the operator review queue. The operator does not get an email or push notification in v1; instead, the operator console raises an in-app "new delivery request" alert. After due diligence, the operator either moves it into the dispatch-ready queue for assignment or sends a short follow-up message back to the merchant.

Below the form, the same page shows all active and recent parcels with status (under review, needs clarification, dispatch ready, assigned, in transit, delivered, failed, in return, returned). The merchant can tap a parcel to see the latest basic details, any operator follow-up message if one exists, and proof status if it exists. The signed-in merchant workspace stays intentionally thin: request capture, status visibility, lightweight follow-up handling, remittance visibility, and billing visibility, but no agreement editing or deep merchant admin tools.

### Journey 11 — Merchant: review finance documents (per cycle)

The merchant opens either the finance area inside the approved merchant workspace or a tokenized document link the operator shared. The merchant can view the remittance statement for a cycle and, separately, the billing invoice for service charges. Remittance shows parcel-by-parcel collected COD, fees deducted, VAT, and net payable. Billing invoice shows service charge line items and the amount owed to the operator. The merchant can download PDFs for both.

There is still no in-app dispute workflow, no signature flow, and no merchant-side finance configuration. Disputes happen through the operator.

## 5. Feature inventory by surface

Each feature below is in v1. Anything not on this list is not in v1.

### Operator console

- **Merchant management:** Create a merchant. Review merchant registrations. Approve, reject, or suspend merchant access. Edit merchant agreement parameters (route or zone-based delivery fees, COD handling fee, tax treatment, remittance cycle, dispute window, default proof requirement, default reattempt limit, default RTO cost allocation rule). Deactivate a merchant.
- **Rider management:** Create a rider profile. Create rider access. Set the rider's PWA login. Mark a rider as active or inactive. Remove rider access. View a rider's history.
- **Order intake:** Merchant request entry as the default path, plus manual single-order entry by ops as a fallback. QR label generation with print view (one label per parcel, A4 sheet of labels for batch printing).
- **Dispatch board:** List of unassigned parcels grouped by merchant. List of riders with status. Build a manifest by tapping parcels into a rider's pending manifest. Manifest preview (count, expected COD, pickups, rough zone). Assign manifest to rider.
- **Live ops view:** Per-rider cards showing current state, parcels in custody, parcels delivered today, cash held, last event time. Anomaly highlighting.
- **Parcel detail and event log:** View any parcel's full state and complete event log with proof artifacts.
- **Finance module:** An admin-only money hub with sections for reconciliation, COD drop, remittances, billing invoices, tax math, CSV exports, and email outbox/history.
- **End-of-shift reconciliation:** Per-rider reconciliation screen with parcel and cash columns, rider cash handover recording, variance highlighting, reason code entry, close-shift action, and exportable shift summary.
- **RTO and reattempt queue:** List of failed parcels in the reattempt queue. After the configured attempt limit, parcels enter the return-to-merchant flow. Operator can override the attempt count, mark a parcel as returned to merchant, or escalate a parcel out of the queue.
- **Merchant remittance:** Draft statement view per merchant per cycle. Finalize, email, download as PDF or CSV, mark as settled with payment method and reference, and hold disputed amounts.
- **Merchant billing invoices:** Draft, issue, email, export, and record paid/void status for merchant billing documents that are separate from remittance.
- **Tax and export tools:** Export reconciliation, COD drop, remittance, billing, and tax reports as CSV.
- **Finance email outbox/history:** Show queued, sent, and failed finance emails with retry capability.
- **Search and dispute lookup:** Find a parcel by AWB, customer phone, or merchant + date.

### Rider PWA

- **Sign in.** Simple sign-in tied to the rider profile. Persistent session.
- **Manifest acceptance.** See the assigned manifest, accept it, start the shift.
- **Pickup flow.** Visit each pickup location, scan parcels, confirm pickup, report mismatch.
- **Parcel list.** See all parcels currently in custody, sortable by manual order or grouped by area.
- **Delivery flow.** Per-parcel screen with customer details, arrival action, three primary outcomes (delivered, failed, partial), photo capture, OTP entry, cash confirmation, variance recording.
- **Failed attempt flow.** Reason code selection, optional photo, return to manifest list.
- **Partial delivery flow.** Cash entry, variance reason, item-level returned marking, photo, return to manifest list.
- **End-of-shift summary.** Self-view of the shift's outcomes, cash to drop per merchant, "Ready to drop" action.
- **Personal cash float view.** A small running total of the rider's own change-making float, separate from collected cash.

### Merchant surface

- **Pending approval view.** A clear blocked state after public registration until an operator approves access.
- **Delivery request form.** A lightweight single-request form for the merchant to submit a parcel directly into the operator queue.
- **Parcel status list.** All parcels for this merchant, current state, last update timestamp, optional delivery photo.
- **Parcel detail.** Customer name (masked), state, full state history at a high level (without rider names or precise geolocation), delivery photo if available.
- **Remittance statement view.** Itemized statement per cycle, downloadable as PDF.
- **Billing invoice view.** Service billing document per cycle or invoice event, downloadable as PDF.

## 6. Cross-cutting concerns

### Notifications

Indek uses two outbound channels in v1: in-app alerts and narrowly scoped transactional delivery.

- **To the rider PWA**, when a manifest is assigned to them. In-app notification, with a small audible cue if the PWA is open.
- **To the operator**, in-app, when a new delivery request lands in the review queue, when a rider taps "Ready to drop", or when an anomaly threshold is crossed (no rider event for 30+ minutes, cash variance forming).
- **To the merchant**, via in-app request status and request-scoped follow-up inside Indek, plus transactional email for approval notices, remittance statements, and billing invoices.

There is no SMS, no marketing email, and no push notifications outside the rider PWA in v1.

### Offline tolerance on the rider PWA

The rider PWA must be usable when connectivity drops, because UAE basements, parking lots, and elevators all kill 4G signal. The minimum offline behavior for v1:

- The current manifest and all parcel details are cached locally on shift start.
- Delivery, failed-attempt, and partial-delivery events captured offline are queued locally and synced when connectivity returns.
- Photos taken offline are stored locally and uploaded on reconnection.
- The rider sees a clear "offline — N events pending sync" indicator when offline, and a "synced" confirmation when reconnected.
- Cash ledger updates are computed locally from queued events so the rider always sees the right running total.

The operator console assumes connectivity. If it drops, the operator stops working until it returns. This is acceptable in v1.

### Time and timezone

Everything in the system runs on UAE time (Asia/Dubai, UTC+4). No multi-timezone support in v1.

### Accessibility

The rider PWA targets the lowest common denominator: budget Android, small screen, sometimes one-handed, sometimes in bright sunlight. High contrast, large tap targets, no hover-dependent interactions, minimal text.

## 7. Out of scope for v1

These are things people will ask for that are not in v1:

- Rider-to-rider custody transfer flow (deferred to v1.1; if it happens before then, it's a manual operator-mediated event)
- Multi-shift days for a single rider (one shift per rider per day in v1)
- Rider chat or messaging within the app
- WhatsApp integration
- Operator analytics dashboards beyond the live ops view
- Heatmaps, time-of-day analysis, rider performance scoring
- Customer-facing tracking
- Self-service merchant agreement editing
- Merchant-initiated disputes
- Multi-language UI
- Native mobile apps
- Push notifications outside the PWA
- Bulk operations on the dispatch board (drag-multiple, etc.)
- Search and filter beyond the basic dispute lookup
- Rider payroll views or pay calculation
- Print views beyond QR labels, remittance PDFs, and billing invoice PDFs
- Integration with Shopify, WooCommerce, accounting software, or anything else
- Any feature that requires Indek to hold, pool, or process funds
